How Codex Is Controlled

AGENTS.md acts as the operating contract for the AI agent.

  • make safe, minimal, well-verified changes
  • follow repo rules and the documented repo structure instead of broad guesswork
  • use the Repo Shape section to locate apps/web, apps/api, shared packages, infra, config, and docs before editing
  • preserve major product constraints such as single live room per team
  • treat the 200-user target as a real design constraint
  • use the shared command discipline around ./dev.sh, including build, typecheck, test:unit, test:int, test:web, and stack commands
  • before closing a task, report any verification gaps explicitly
  • update private worklogs and public docs for non-trivial work

Result: less random AI behavior, stronger consistency, and lower risk of hidden regressions.

Key Requirements for AI Agents

The repository gives AI agents a small set of non-negotiable working rules.

  • prefer targeted reads over broad scans
  • start from the Repo Shape map so frontend, backend, shared, infra, and docs responsibilities are clear
  • keep behavior, docs, and tests aligned in the same task
  • preserve core product constraints such as one live room per team
  • treat the 200-user session target as a real engineering limit
  • use the basic shared command surface instead of ad hoc workflows: typecheck, test:unit, test:int, test:web, test:full, stack:up, stack:down
  • run the nearest relevant verification before and after meaningful changes
  • keep simulator-backed suites serial so the results stay trustworthy
  • before closing a task, report any verification gaps explicitly
  • update private worklogs and public docs for non-trivial changes

These rules make the AI more predictable and reduce accidental scope drift.

How the Docs Orient the Agent

Document Network

  • README.md: product overview and command surface
  • USAGE.md: run, verify, and operate the system
  • ARCHITECTURE.md: system shape and runtime model
  • public docs: product, operator, contributor, architecture, and release guidance
  • role-focused docs: user guidance plus dedicated team-admin and super-admin operation guides

  • private planning context: what is in scope now, what is done, and what still needs proof

Effect on AI Work

  • faster access to the current truth
  • less wasted rediscovery from raw code only
  • clearer distinction between stable rules and in-progress work
  • fewer wrong assumptions before edits begin

Spec-Driven Development

The project uses living documentation, not only tickets or chat history.

  • public docs for product direction and operator expectations
  • private planning notes for active delivery streams
  • architecture notes for technical decisions and explicit architecture changes
  • private worklogs for change history and verification trail
  • release notes and changelogs for public-facing change history

That keeps requirements visible during implementation and allows work to resume later without losing intent.

Frontend Safety and React Guidance

project_docs/REACT_PERFORMANCE_GUIDELINES.md gives Codex explicit frontend rules.

  • measure first, then optimize
  • avoid complexity without proof
  • keep before/after evidence for performance-sensitive changes
  • check rerender boundaries and state shape
  • verify form containment, adaptive layout, panel reachability, and escape paths
  • tie UI changes back to concrete checks instead of trusting a single happy-path screenshot

These rules reduce a common AI failure mode: UI that looks acceptable in one state but breaks in edge cases.

Testing and Verification Layers

  • unit tests for logic, decks, and result calculation
  • integration tests for backend and persistence flows
  • web tests for frontend behavior
  • packaged end-to-end tests for real user journeys
  • perf-focused checks such as test:web:perf and test:e2e:perf
  • simulator-backed layout and heavy multi-user conditions
  • the command surface mirrors those layers through test:unit, test:int, test:web, and broader verify flows
The project does not rely on "it seems to work". It relies on layered verification.

Simulation and Demo Support

  • dev/test simulator with seeded users and teams
  • super-admin demo-mode direction for realistic presentations and stakeholder demos
  • simulator-backed suites such as test:e2e:sim and test:e2e:sim:matrix21 exercise multi-user and layout-heavy conditions

Why simulation matters

  • makes realtime behavior repeatable
  • lets one developer reproduce many-user coordination patterns without gathering a live audience
  • helps validate crowded-room layouts
  • supports performance and concurrency testing
  • supports proof-first serial verification because the simulator-backed suites share packaged stack resources
  • makes demos more realistic than static screenshots because rooms, votes, reveals, and role behavior can be shown live

Performance, Capacity, and Evidence

Performance is treated as a real engineering concern and is validated under deliberately heavy synthetic load.

  • single-room stress: 200 simultaneous users
  • multi-room stress: 200 + 20 x 10 users across many rooms
  • burst stress: 80 near-simultaneous actions
  • saved evidence: ./dev.sh phase:p3:verify writes latest markdown and JSON artifacts
Small heavy burst 53ms Average burst vote latency for `80` simultaneous users, with a second burst at `49.87ms`.
Super-big single room 150ms Average user vote latency in the `200`-user room, with `p95 237.5ms`.
Parallel rooms under load 176ms / 384ms Main-room user vote latency `176.48ms`; side-room user latency `383.95ms` during `200 + 20 x 10` load.
Correctness under stress 20 / 20 Late votes after reveal were rejected in every measured case, while reveal convergence stayed around `154ms` to `336ms`.

Future Tasks for AI-Assisted Software Development

The next step is to keep turning this project experience into reusable, tool-neutral AI engineering practices.

1. Curate reusable AI-development practices

  • Review useful agent-workflow ideas, templates, and productivity patterns before adopting them into this repository.
  • Identify which practices can strengthen our repository guidance, agent instructions, prompts, and task workflows.
  • Separate generic AI-development improvements from tool-specific Claude Code conventions.

2. Transfer the combined improvements across AI tools

  • Translate the best Codex and Claude-style practices into clear repository instructions and reusable workflows.
  • Keep tool-specific details isolated so the project remains understandable to humans and different agents.
  • Keep the same expectations: documented context, scoped tasks, repeatable verification, and explicit closeout evidence.

3. Create reusable project kits

  • Prepare starter guidance files for common project types, including React frontend projects and API/backend services.
  • Package reusable AI instructions, architecture templates, testing expectations, worklog rules, and verification checklists.
  • Treat this as the hardest and highest-value target: a practical AI-assisted development system that can be copied into real delivery projects.

Final Message
